## Overview

AMO stores reasoning in three levels. Each level has a different responsibility and mutation rule.

```text
Level 1: Raw Session Events
        -> Level 2: Session Summary Graph
        -> Level 3: Central Graph
```

All three levels carry repository scope when the evidence is tied to code. The
scope key is `repo_id`, derived from configured repo UUID, normalized Git
remote, or Git-root fallback. `repo_path` is retained only as local debug
metadata because paths differ across machines.

## Level 1: Raw Session Events

Raw session events are append-only evidence. They include hook payloads, transcript events, tool calls, tool outputs, user prompts, visible assistant messages, and stop/finalize records.

Raw evidence is noisy by design. It is allowed to contain command output, repeated prompts, failed attempts, and irrelevant context. Raw evidence is not answer memory. It is the audit trail used to rebuild extracted graphs.

Mutation rule: never edit or delete raw evidence. If redaction policy changes, write a new redacted derived record and keep provenance to the original raw evidence ref.

## Level 2: Session Summary Graph

The session summary graph is the cleaned, structured, per-session reasoning graph. It contains decision threads, decision units, code nodes, code hunks, tests, bugs, fixes, and relationships.

Session graph nodes are immutable provenance for one closed-session job and one
resolved repository. They carry `session_id`, `job_id`, `repo_id`, and local
`repo_path`. Two sessions from different repositories must not share central
identity even if their files or symbols have the same names.

This graph is generated by an `ExtractionRun`. Re-running extraction creates a new `ExtractionRun` and a new set of derived nodes. It must not overwrite raw evidence.

A session graph is queryable by itself. It should answer questions such as:

```text
What decisions were made in session X?
What files were touched and why?
Which code hunk did this decision produce?
Which test validated the fix?
```

Mutation rule: extraction outputs are append-only per run. The selected/finalized run is marked by status and metadata, not by deleting other runs.

## Level 3: Central Graph

The central graph is the reconciled cross-session graph. Only finalized session graph nodes can merge into it. It contains durable active, committed, superseded, refined, contested, and abandoned knowledge.

The central graph is append-only at the knowledge level. Old nodes remain queryable. Version relationships and statuses express changes over time.

Central graph identity is repo-scoped:

```text
repo_id + canonical_key -> KnowledgeAtom
session graph node      -> KnowledgeVersion -> VERSION_OF -> KnowledgeAtom
GraphView(repo_id, main, active) -> latest GraphCommit for that repo
```

This lets one AMO install track many projects while keeping canonical atoms,
branch-head locks, graph commits, active views, retrieval docs, vectors, and
dashboard filters separated by repository.

Mutation rule: central merge may update statuses and add edges, but must not delete historical nodes or mutate stored embeddings in place.

## Boundaries

Raw nodes are provenance. Session graph nodes are extraction artifacts. Central graph nodes are durable memory.

A normal answer should not use raw evidence or draft session nodes unless the query explicitly asks for raw/current-session evidence. This boundary prevents polluted raw data from becoming product memory.

For code questions, retrieval should use the selected repo's active
`GraphView`. Global/all-repo views are operator diagnostics; they are not the
ideal answer path when the user is currently working inside a specific
repository.
